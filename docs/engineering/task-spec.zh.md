# task-spec：让规划服务于判断

[English](./task-spec.md) | 中文版

[技能正文](../../skills/engineering/task-spec/SKILL.md) 帮助 agent 判断需要多少规划、哪些问题
值得调查，以及何时应更新方案。目标是用证据完成用户意图，而不是让每个任务经过固定阶段。

## 用户要求具有约束力，实现计划可以调整

用户指令、约定行为、权限和明确审批关卡是约束。模型自己写的计划是满足约束的一种工作假设，
不能悄悄缩窄原始请求，也不能推翻用户指定的程序。

因此，发现已有工具函数、合并步骤或修正假设时，可以在约束内直接调整，不必重启任务。
但用户明确批准的实现选择或执行程序仍需遵守；适应变化不是擅自偏离授权的理由。

验证要回到原始请求和实际结果。例如用户要求保留重复名称，模型草拟的标准却写成去重排序，
应纠正草稿和实现，不能以满足错误草稿为完成依据。

## 规划深度取决于不确定性和后果

明确、可逆的常规工作可以检查后直接执行，用定向检查结束。有实质依赖或方案取舍时，写清
简短思路和可观察的验收标准。难以撤销的决策则应在承诺前呈现假设、保障、恢复和验证方式。
一条破坏性命令可能比大量机械修改更需要规划。

这些是判断示例，不是必须宣告的任务等级。不规定备选方案、边界情况或简化建议的数量。
只调查能影响决策的问题；隔离、可逆的小实验有时比长篇推演更能解决疑问。

交接、长期工作或用户明确要求时，才需要持久化计划。[模板](../../skills/engineering/task-spec/references/spec-template.md)
是可选提纲，保留当前方案和有用的决策历史即可。只要求方案的任务，以交付方案及说明限制结束，
不自动进入执行。

## 根据失效的是哪项判断，决定回到哪里

| 新证据或失败 | 对应动作 |
|---|---|
| 局部实现错误 | 修复并重跑受影响检查 |
| 发现更好的实现细节 | 在约束内直接调整 |
| 设计假设不成立 | 重审该决策和依赖它的步骤 |
| 要求或权限冲突 | 在依赖动作前解决约束或获取决策 |

这替代了“任何验证失败都重新探索、定规、挑战、执行、审查”的规则。反复失败仍须改变诊断、
寻求针对性帮助或报告阻塞；允许局部修复不意味着无限打补丁。复杂子步骤也不自动复制完整流程。

## 独立审查是一种工具，不是两道必经关卡

用户明确要求、不可逆承诺依赖关键假设，或存在重要分歧与不确定性时，使用独立检查。
若 `adversarial-review-loop` 可用，可对相关方案或改动使用它的只审查模式，传递原始要求和
证据来源。修复由任务负责人处理一次，并验证受影响结果。

常规工作不依赖另一个审查技能。独立意见不能证明备份可恢复，也不能授予权限。缺少独立
审查者或必要证据时，应报告缺口，不能当成已验证。

## 删除了什么，保留了什么

旧版要求所有任务触发、模型自拟计划不可偏离、挑战配额、双重独立关卡、完整循环重启和递归
阶段流程。这些机制让可以直接判断的局部问题也支付固定成本。新版保留目标理解、范围控制、
真实取舍、证据和对重要问题的独立审视。

规划深度和验证是否足够仍依赖判断，提示词变短不能证明判断永远正确。
[行为案例](../../skills/engineering/task-spec/evals/evals.json) 覆盖常规修复、错误计划纠正和高风险
只交付方案的请求。正文缩短不等于已测得运行 token 或时间降幅，后者需要可比的重复运行。
