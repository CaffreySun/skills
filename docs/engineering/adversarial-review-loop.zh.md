# adversarial-review-loop：让判断力决定审查强度

[English](./adversarial-review-loop.md) | 中文版

[技能正文](../../skills/engineering/adversarial-review-loop/SKILL.md) 的目标是：在合理成本内，
发现并解决影响结果的实质问题。默认信任审查者的常规判断，在风险、不确定性或分歧使额外
检查有价值时，再引入独立视角。疑点数量不是质量指标。

## 2.0 改变了什么

旧版通过逐条独立裁决、默认编排代理、复审更换上下文和归零循环来补偿潜在错误。
每道保障各有理由，但简单修复也要支付组合后的成本。把中间输出移出主上下文，并没有
消除整个系统的阅读、传递和报告工作。

新版默认 **审查 → 处理有依据的问题 → 选择适当验证**。主代理直接协调，审查者自行调查
和排除弱猜测。重要分歧、高影响但证据不足的主张，以及不可逆决策所依赖的关键假设，才需要
额外独立检查。不再为每个放弃的疑点撰写反证。重要未知必须明确报告，不能伪装成已证实的
缺陷，也不能当成通过。

## 两种模式仍按修复归属区分

- **只审查／judge-only**：返回有依据的问题和重要未知，修复及再次进入由调用方负责。
- **审查并修复／full round**：完成已授权、范围内的修复，验证实际结果。只要求审查不等于
  授权修改。

`task-spec` 在重要问题需要审查时使用 judge-only，由任务负责人修复，并回到实际失效的实现或决策。调用方仍可要求旧版判决名称，
但名称不再强制逐条独立裁决。发现更大原因也不等于获得重新设计的授权。

## 验证方式取决于风险

明确的局部修复可以用定向测试或一致性检查结束；契约变化需要检查受影响的依赖；重要风险
未决时才追加针对性的独立复审。原审查者可以检查修复，最终状态仍适用的证据可以复用。

验证实际修改，包括相关新增文件，不假定建议补丁已原样落地。需要时可保存快照或基线。
追加审查必须指出具体的实质风险和有用的下一项检查，不能因为反复猜测而不断开新一轮。
达到成本边界时报告剩余风险与下一步，不把时间耗尽包装成验证通过；零发现也不能证明绝对正确。

## 如何评价升级

用局部修复、跨文件改动和高风险方案检查质量与克制：关键缺陷是否找到，是否产生猜测性修改，
是否遵守只读边界，重要不确定性是否得到升级处理。
[评估案例](../../skills/engineering/adversarial-review-loop/evals/evals.json) 保存在技能目录内。

正文缩短、强制交接减少，说明规定动作减少了。实际 token 和耗时收益需要可比的执行轨迹；
文件体积下降和场景检查不能单独证明运行成本下降，也不能证明所有任务都保持相同质量。
